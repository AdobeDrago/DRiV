DrivParts · Pilot

DrivParts EDS Pilot

A pilot validating DrivParts' migration to Adobe Edge Delivery Services (EDS), and confirming EDS can power dynamic, backend-driven experiences — parts catalog search, retailer lookup, and an embedded Hybris storefront — not just static marketing content. Four reference journeys from the production DrivParts site drive the work. This guide tracks the architecture, engineering approach, and progress to date.

Purpose

  • Validate migration of DrivParts marketing and commerce-adjacent pages to Edge Delivery Services.
  • Validate support for dynamic, backend-driven experiences (catalog APIs, Where to Buy, Hybris session).

Core engineering requirements

  • Use the EDS block-based development model only (scripts/aem.js + scripts/scripts.js).
  • Integrate backend services: MOOG/DrivParts catalog APIs, Where to Buy servlet, Hybris storefront.
  • Support region and language switching via DrivParts header/footer locale pickers.
  • Route DrivParts-specific blocks through blocks/drivparts/* with a modular service layer (catalog.js, storefront-session.js) and Cloudflare Workers for CORS/proxy.

Install & run

  1. Clone and install
    git clone https://github.com/AdobeDrago/DRiV.git cd DRiV npm install

    Also runs Husky via the prepare script, installing the repo's pre-commit hook.

  2. Run the AEM CLI
    sudo npm install -g @adobe/aem-cli aem up

    Starts the standard EDS local dev server at http://localhost:3000, proxying content from the linked Document Authoring (https://da.live) source.

Linting & CI

npm run lint # runs lint:js + lint:css npm run lint:js # ESLint (airbnb-base) npm run lint:css # Stylelint (blocks/**/*.css, styles/*.css)
.github/workflows/main.yaml runs npm run lint on every push — it does not run a build, deploy, or test step. There is no automated test suite in this repo, and lint isn't enforced by a git hook.

Hybris proxy for local dev

Pages under /drivparts embed a Hybris storefront iframe. That storefront enforces CSP frame-ancestors and cookie rules that block a bare localhost:3000 iframe, so local development uses tools/fmstorefront-proxy.mjs to put EDS and the Hybris paths behind one origin.

  1. Terminal 1 — AEM dev server on a secondary port
    aem up --port 3001 --no-open
  2. Terminal 2 — the storefront proxy, listening on :3000
    npm run proxy

    Browse http://localhost:3000/. The proxy forwards /fmstorefront, /medias, /fmwebservice, and /content/dam to the Hybris QA origin (STOREFRONT_ORIGIN, default qa.drivparts.com) and everything else to the local AEM server on :3001 (AEM_ORIGIN). It rewrites hostnames, strips X-Frame-Options/frame-ancestors, and normalizes Set-Cookie so the storefront session survives on localhost.

Block-loading routing

scripts/aem.js is otherwise the standard EDS/Helix boilerplate. The one deviation from stock is in block resolution: a block's CSS/JS is normally loaded from blocks/{name}/, but three constructs reroute specific blocks to blocks/drivparts/{name}/ instead.

const DRIVPARTS_BLOCKS = new Set([ 'parts-finder', 'part-finder-result', 'part-details', 'parts-list', 'where-to-buy-search', 'where-to-buy-result', 'hybris-storefront', 'columns-promo', 'hero-banner', 'brand-detail', 'brand-nav', 'widget', 'embed-signin', ]); // always resolve under blocks/drivparts/ const DRIVPARTS_OVERRIDES = new Set([ 'header', 'footer', 'fragment', 'cards', 'columns', 'hero', ]); // resolve under blocks/drivparts/ only on /drivparts pages

getBlockBasePath(blockName) checks both sets and returns either blocks/drivparts/{blockName} or the normal blocks/{blockName}; loadBlock() uses it to build the CSS/JS URLs it loads.

Journey 4 — Hybris Storefront Complete

Journey 4 validates embedding the Hybris commerce storefront beside EDS marketing and Parts Finder: same-origin iframe (CSP frame-ancestors 'self'), anonymous / CSR / emulating auth modes, header mini-cart, parts-list → add-to-cart, and login-return recovery when Hybris redirects off the EDS page.

Live (production / QA): https://qa.drivparts.com · iframe path /fmstorefront/federalmogul/en/USD/iframe?site=federalmogul
Building (EDS): https://code-and-theory--driv--adobedrago.aem.page/drivparts/ complete — requires same-origin Hybris routes
Live URL (POC): https://drivparts-eds-poc.atul-code-auth0.workers.dev/drivparts/

  • Same-origin Hybris proxy
    Local: tools/fmstorefront-proxy.mjs (npm run proxy). POC: drivparts-eds-poc. Production-oriented: drivparts-hybris-proxy. All rewrite Location / cookies / strip frame-ancestors so /fmstorefront, /medias, /fmwebservice, /content/dam share the EDS origin.
  • Embed storefront iframe on EDS pages
    hybris-storefront loads a same-origin <iframe> (default STOREFRONT.iframe). Probes reachability; shows a local-proxy hint if framing fails. Syncs layout for anonymous / CSR / emulating modes.
  • Auth modes + header session UI
    Anonymous (Get More + Sign In), CSR (Emulate Account), emulating (B2B Account Details). Header listens for storefront:auth, shows Welcome / cart / End Emulate, and binds mini-cart popup via fetchMiniCartDetails().
  • Parts list → Hybris add-to-cart
    submitPartsListToCart() in storefront-session.js POSTs the saved parts list to Hybris (full-page form submit, same as QA). Guests redirect to sign-in; authenticated / emulating sessions continue to cart.
  • Login-return recovery
    On login / emulate, sessionStorage['fm-login-return'] stores the EDS URL. scripts.js bounces users stranded on raw /content/ or /fmstorefront/ paths back to that page. Iframe login form stays target="_self" so the parent isn’t replaced.
  • Production proxy binding
    drivparts-hybris-proxy and catalog/contact workers still deploy to *.workers.dev; custom domain routes are commented until the production zone is decided. POC EDS_ORIGIN may point at a feature branch — confirm before demos.

Successful upstream responses get Cache-Control: public, max-age=86400 and an X-Cache: HIT/MISS header. CORS is open. No secrets required.

drivparts-eds-poc

A combined "front door" that merges EDS pages and the Hybris storefront under one origin. Hybris paths (/fmstorefront/, /medias/, /fmwebservice/, /content/dam/, plus _Incapsula_Resource) go to HYBRIS_ORIGIN (https://qa.drivparts.com); everything else goes to EDS_ORIGIN. It handles extensive Location/cookie/CSP rewriting, short-circuits cart-fragment AJAX requests with a 204 to avoid a document.write DOM-wipe bug, and sets cache-control: no-store on Hybris responses.

Current EDS_ORIGIN value: https://code-and-theory--driv--adobedrago.aem.page/drivparts/ — a feature-branch preview URL, not production or main. Update it before using this worker beyond throwaway testing.
Its wrangler.toml sets compatibility_date = "2026-07-28", while the other three workers use 2024-09-23. Worth confirming this is intentional.

Deploying

From the repo root, once authenticated (npx wrangler login):

npm run deploy:catalog-api npm run deploy:eds-poc

Each script is a thin wrapper around wrangler deploy -c workers/<name>/wrangler.toml. Local storefront development uses the proxy in Hybris proxy for local dev instead of these workers.

Overview

A pilot validating MoogParts' migration from AEM Managed Services to Edge Delivery Services. Moog is a single-brand chassis site: homepage marketing bands, a Parts taxonomy (Steering / Suspension / Driveline / Wheel End), Find My Part catalog search, and Support content — plus locale trees for NA and EMEA.

Purpose

  • Migrate MoogParts marketing, Parts catalog, and Support content to EDS with DA authoring under market/locale paths (/na/en-us, /emea/en-eu, …).
  • Replace the legacy AngularJS Find My Part SPA with EDS blocks + Cloudflare catalog proxy.
  • Preserve Moog's primary journeys from the live site mega-nav: Parts, Support, Technologies, Find My Part.

Core engineering requirements

  • EDS block-based model only (scripts/aem.js + scripts/scripts.js).
  • Catalog / cross-sell / FMMP via moogparts-catalog-api; contact submit via moogparts-contact-proxy.
  • Locale path prefixes via getLocalePrefix() (flat /en-us or nested /na/en-us, /emea/en-eu).

Getting Started

  1. Clone and install
    git clone https://github.com/codeandtheory/moogparts-prototype.git cd moogparts-prototype npm install
  2. Run the AEM CLI
    aem up

    Local EDS server at http://localhost:3000, content from DA (codeandtheory/moogparts-prototype). Start at /na/en-us/.

  3. Lint
    npm run lint

    CI runs lint on every push. Run after JS/CSS changes (including workers/*/index.js).

Journey 3 — Find My Part Complete

Journey 3 replaces the legacy AngularJS Find My Part SPA with EDS blocks backed by moogparts-catalog-api. Visitors search by vehicle (year → make → model cascades) or by part number, land on a results page, open part details, and may see related products. Cross-sell is a step in this flow (results/detail), not a standalone pilot journey.

Live (production): https://www.moogparts.com/find-my-part.html
Building (EDS): https://main--moogparts-prototype--codeandtheory.aem.live/na/en-us/find-my-part → find-my-part-results / find-my-part-num-results → part-details
DA: na/en-us/find-my-part.html, find-my-part/find-my-part-results, find-my-part-num-results, part-details

  • Catalog API via Worker
    Blocks call moogparts-catalog-api…/catalog/* (never the catalog origin directly). Shared params for US: brand=moog, locale=en_US, country_code=US. Worker adds CORS + ~24h edge cache.
  • Search entry (vehicle + part number)
    find-my-part-us appears on the dedicated Find My Part page and as a homepage embed. Light Duty / Medium-Heavy Duty vehicle cascades (year → make → model); part-number path submits to find-my-part-num-results.
  • Render results dynamically
    find-my-part-results-us lists matching parts from the Worker response and builds locale-prefixed deep links to /part-details?brand_code&part_number.
  • Part detail page
    part-details fetches product + applications JSON (often via Worker /drivparts/* routes on the same catalog Worker), then renders gallery, specs, and applications.
